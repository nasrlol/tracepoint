DE KERN IN ÉÉN ZIN
  Er bestaat maar één echte PowerShell-debugger: die van de engine
  (System.Management.Automation.Debugger). Al het andere is een front-end:
  - cmdlets in de console (Set-PSBreakpoint, Wait-Debugger, Debug-Runspace, ...)
  - PowerShell Editor Services (PSES), dat de engine-debugger aanbiedt via DAP
    -> VS Code, Neovim, Helix, IntelliJ/Rider, tdb, ...
  - eigen IDE-integraties die rechtstreeks de engine aanspreken
    -> ISE, PowerShell Studio/PrimalScript, PowerShell Pro Tools (Visual Studio)

WAT DIT BETEKENT VOOR TRACE
  - Elke bestaande tool gaat uit van een mens achter een prompt of editor die
    stap voor stap meekijkt. Geen enkele tool richt zich op "breakpoints met
    acties zetten op veel servers tegelijk, zonder dat het script stilstaat".
    Dat is precies de niche van Trace (niveau 2 tracepoints, niveau 3 attach).
  - Wat Trace doet (NamedPipeConnectionInfo + runspace in het doelproces) is
    hetzelfde mechanisme als Enter-PSHostProcess, en ook wat "PowerShell Attach
    to Host Process" in VS Code en de Helix-attach-config onder de motorkap
    gebruiken (processId + runspaceId = 1). Zie architectuur.md.
  - De beperking uit de PoC ("remote debugging is not supported by the current
    host" bij Set-PSBreakpoint -Runspace) is dezelfde reden waarom tools als
    Add-Debugger.ps1 bestaan: een host zonder debugger-UI moet zelf een
    DebuggerStop-handler leveren. Tracepoints zonder 'break' omzeilen dat.
  - PSES is de enige serieuze herbruikbare backend (DAP over named pipe /
    Unix-socket). Volgens de eigen README zijn de types van PSES niet stabiel om
    tegen te linken. Voor Trace dus beter de engine-API rechtstreeks gebruiken,
    zoals nu.
  - ForEach-Object -Parallel en ThreadJobs draaien in eigen runspaces; een
    breakpoint op runspace 1 vangt die niet. Trace moet Get-Runspace
    breder bekijken als zulke scripts op de vloot draaien (zie 01-ingebouwd.txt).
